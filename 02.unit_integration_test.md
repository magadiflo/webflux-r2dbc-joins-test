# 🔗 Unit & Integration Test | Spring Data R2DBC

---

## ⚙️ Configuración de propiedades (`src/test/resources/application.yml`)

En las pruebas unitarias y sobre todo en las pruebas de integración es importante `aislar el entorno de ejecución`
respecto al de desarrollo.

Para ello, definimos un archivo `application.yml` específico en `src/test/resources/`, que `Spring Boot`
cargará automáticamente al ejecutar los tests de integración.

### 📌 Objetivos de esta configuración

- **Puerto aleatorio (`server.port=0`)** → evita conflictos con la aplicación principal, garantizando que las pruebas se
  ejecuten en un puerto distinto.
- **Base de datos de prueba (`db_webflux_r2dbc_test`)** → asegura que los tests no afecten la base de datos usada en
  desarrollo.
- **Logging detallado** → permite inspeccionar las consultas SQL generadas por R2DBC y verificar parámetros enviados.

### 📝 Configuración

````yml
server:
  port: 0
  error:
    include-message: always

spring:
  r2dbc:
    url: r2dbc:postgresql://localhost:5436/db_webflux_r2dbc_test
    username: magadiflo
    password: magadiflo

logging:
  level:
    dev.magadiflo.app: debug
    io.r2dbc.postgresql.QUERY: debug
    io.r2dbc.postgresql.PARAM: debug
````

## 🗄️ Creación de tablas y datos de prueba

En la fase de pruebas necesitamos replicar la estructura de la base de datos usada en desarrollo, pero en un entorno
aislado. Para ello definimos scripts `DDL` (estructura) y `DML` (datos iniciales) en el directorio
`src/test/resources/sql-test/`.

### ⚙️ Script DDL (`schema.sql`)

Este script crea las tablas necesarias para las pruebas en la base de datos `db_webflux_r2dbc_test`.
La estructura es la misma que en desarrollo, pero se mantiene separada para garantizar independencia entre entornos.

````bash
CREATE TABLE IF NOT EXISTS employees(
    id BIGSERIAL PRIMARY KEY,
    first_name VARCHAR(255) NOT NULL,
    last_name VARCHAR(255) NOT NULL,
    position VARCHAR(255) NOT NULL,
    is_full_time BOOLEAN NOT NULL
);

CREATE TABLE IF NOT EXISTS departments(
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(255) NOT NULL UNIQUE
);

CREATE TABLE IF NOT EXISTS department_managers(
    department_id BIGINT,
    employee_id BIGINT,
    CONSTRAINT pk_dm PRIMARY KEY(department_id, employee_id),
    CONSTRAINT fk_departments_dm FOREIGN KEY(department_id) REFERENCES departments(id),
    CONSTRAINT fk_employees_dm FOREIGN KEY(employee_id) REFERENCES employees(id),
    CONSTRAINT uk_department_id_dm UNIQUE(department_id),
    CONSTRAINT uk_employee_id_dm UNIQUE(employee_id)
);

CREATE TABLE IF NOT EXISTS department_employees(
    department_id BIGINT,
    employee_id BIGINT,
    CONSTRAINT pk_de PRIMARY KEY(department_id, employee_id),
    CONSTRAINT fk_departments_de FOREIGN KEY(department_id) REFERENCES departments(id),
    CONSTRAINT fk_employees_de FOREIGN KEY(employee_id) REFERENCES employees(id),
    CONSTRAINT uk_employee_id_de UNIQUE(employee_id)
);
````

#### 📌 Observaciones

- Se usan `IF NOT EXISTS` para evitar errores si las tablas ya existen.
- Las tablas de relación (`department_managers`, `department_employees`) tienen constraints para garantizar integridad
  referencial y unicidad.
- La estructura refleja las relaciones entre `Department` y `Employee` (manager y empleados).

Se ubica en `src/test/resources/sql-test/data.sql`.

## ⚙️ Inicialización de scripts SQL

En pruebas de integración necesitamos que la base de datos de prueba se inicialice automáticamente con la estructura
(`DDL`) y los datos (`DML`) definidos previamente. Para lograrlo, creamos una clase de configuración específica para el
entorno de test usando `@TestConfiguration`.

📂 Ubicación: `src/test/java/dev/magadiflo/app/config/TestDatabaseConfig.java`

````java

@TestConfiguration
public class TestDatabaseConfig {
    @Bean
    public ConnectionFactoryInitializer initializer(ConnectionFactory connectionFactory) {
        Resource schema = new ClassPathResource("sql-test/schema.sql");
        Resource data = new ClassPathResource("sql-test/data.sql");
        ResourceDatabasePopulator resourceDatabasePopulator = new ResourceDatabasePopulator(schema, data);

        ConnectionFactoryInitializer initializer = new ConnectionFactoryInitializer();
        initializer.setConnectionFactory(connectionFactory);
        initializer.setDatabasePopulator(resourceDatabasePopulator);
        return initializer;
    }
}
````

### 📌 Explicación

- `@TestConfiguration`
    - Es una variante de `@Configuration` pensada para pruebas.
    - Permite definir beans adicionales o personalizados que solo estarán disponibles en el contexto de test.
    - No afecta la configuración de la aplicación principal, garantizando aislamiento entre producción y pruebas.

- `ConnectionFactoryInitializer`
    - Se encarga de inicializar la base de datos de prueba al arrancar el contexto.
    - Usa el `ConnectionFactory` para establecer la conexión.
    - Ejecuta los scripts SQL definidos en el `ResourceDatabasePopulator`.

- `ResourceDatabasePopulator`
    - Ejecuta los scripts `schema.sql` y `data.sql` ubicados en el classpath (`src/test/resources/sql-test/`).
    - `schema.sql` crea las tablas necesarias.
    - `data.sql` inserta datos iniciales para las pruebas.
